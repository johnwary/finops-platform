## Findings

### BLOCKER

#### S1 — Hardcoded auth secret can reach production via NODE_ENV hole
`apps/api/src/lib/env.ts:3,8,19`

```ts
const isProd = process.env.NODE_ENV === 'production';   // raw, computed before Zod runs
const requiredInProd = (devDefault) =>
  isProd ? z.string().min(1) : z.string().min(1).default(devDefault);
BETTER_AUTH_SECRET: requiredInProd('dev-secret-do-not-use-in-prod'),
```

`isProd` is derived from the raw env at module top, before Zod's `NODE_ENV` enum validation. The dev fallback engages for **every** `NODE_ENV` value that is not the exact literal `'production'`. Holes:
- `NODE_ENV` unset → defaults to `development` in Zod, but `isProd` already false → weak secret silently accepted.
- `NODE_ENV=prod` / `Production` / `staging` / any typo → `isProd` false → weak secret accepted (the enum check rejects the value only *after* `isProd` was computed, and only if it is set to a non-enum string).

Concrete risk: the hardcoded, guessable secret `dev-secret-do-not-use-in-prod` signs/verifies production session cookies → **session forgery**. Same root cause degrades `DATABASE_URL` and `BETTER_AUTH_URL` (see S3).

**Fix:** delete the three dev defaults; require `BETTER_AUTH_SECRET` / `DATABASE_URL` / `BETTER_AUTH_URL` in every deployed environment (keep dev values in `.env` / `.env.example`, not in source). Closes S1 + S3 + S5.

### HIGH

#### S2 — Destructive scripts guard on NODE_ENV label, not DB host
`apps/api/prisma/clear-app-data.ts:9,18-21` + `apps/api/prisma/seed.ts:18-21`

Both destructive scripts guard only on `NODE_ENV === 'production'` — an env-label check, not a check of where `DATABASE_URL` actually points. `DATABASE_URL=<prod-url> pnpm api:data:clear --yes` with an unset/`development` NODE_ENV wipes Loans, Payments, the CapitalEntry ledger, Borrowers, Deposits (User/Account preserved). `clear-app-data.ts:9` also exposes `--allow-production` to bypass the guard entirely.

**Fix:** additionally refuse when `DATABASE_URL` host ∉ {localhost, 127.0.0.1} unless an explicit flag + typed DB-name confirmation is given.

#### S3 — Secure cookies not guaranteed in production
`apps/api/src/lib/auth.ts` (no `advanced` / cookie block present)

better-auth 1.6.20 derives cookie `secure` from whether `baseURL` (`BETTER_AUTH_URL`) is `https://`. If `BETTER_AUTH_URL` is unset in a deployment, the S1 fallback makes it `http://localhost:3000` → session cookie is **not `Secure`** → can leak over plaintext. (`httpOnly: true`, `sameSite: 'lax'` defaults are fine.)

**Fix:** `advanced: { useSecureCookies: env.NODE_ENV === 'production' }`, or guarantee an https `BETTER_AUTH_URL` (folds into S1's required-in-prod fix).

### MEDIUM

#### S4 — No dedicated auth rate limit; global bucket is generous
`apps/api/src/index.ts:80-88`

A single global `express-rate-limit` (`windowMs: 15min`, `limit: 2000` per IP) covers `/api/auth/*` (correctly mounted before the auth handler). But login / reset-password are not throttled more tightly than any other route → credential-stuffing headroom. better-auth's own `rateLimit` is not configured (`auth.ts`).

**Fix:** add a stricter limiter (e.g. 10–20 / 15min) on `/api/auth/sign-in` and `*reset*`.

#### S5 — CORS / trustedOrigins silently fall back to localhost in misconfigured prod
`apps/api/src/lib/env.ts:13,23` + `apps/api/src/lib/auth.ts:24-28`

`CORS_ORIGIN` and `WEB_URL` have dev defaults, no prod requirement, and `CORS_ORIGIN` is not `.url()`-validated. Not a wildcard (safe from origin reflection), but a misconfigured prod resolves these to `http://localhost:5173` rather than the real origin, so CORS + CSRF-origin trust would be wrong. Inherits S1's root cause.

**Fix:** require `CORS_ORIGIN` / `WEB_URL` in prod, and `.url()`-validate them.

### LOW

#### S6 — No CI gate
`.github/workflows/` absent. Nothing runs lint/test/build before an image ships (deployment is Coolify-driven from Dockerfiles).
**Fix:** add CI running `pnpm lint && pnpm test && pnpm build` on PR.

#### S7 — Containers run as root
`apps/api/Dockerfile`, `apps/web/Dockerfile` — no `USER` directive.
**Fix:** add a non-root `USER` in each final stage.

#### S8 — Graceful shutdown skips prisma.$disconnect() + no timeout fallback
`apps/api/src/index.ts:124-132` — SIGTERM/SIGINT call `server.close()` then `process.exit(0)`, but never `prisma.$disconnect()` and have no forced-exit timer if connections hang.
**Fix:** `await prisma.$disconnect()` in the handler + a force-exit timeout.

#### S9 — RBAC applied per-router, not globally at mount
`apps/api/src/index.ts:95-103` mounts routers bare. `borrowers` / `invitations` / `activity` repeat `requireAuth` inline per-route rather than `router.use(requireAuth)`. No live hole today (all routes verified protected), but fragile: a future route added above the guard, or a new router mounted without one, is silently public.
**Fix:** apply `requireAuth` once at the mount layer for all `/api/v1/*` routers (keep `requireRole` per-route); keep the better-auth handler and `/health` before the global guard.

#### S10 — requireEmailVerification:false + autoSignIn:true
`apps/api/src/lib/auth.ts:30-34`. No email-ownership proof. Mitigated by the invite-only `user.create.before` hook (`auth.ts:59-73`) — but the entire signup-abuse defense rests on that single hook. Acceptable by design; noted so it isn't weakened accidentally.

#### S11 — Log redaction is exact-path `req.body.*` only
`apps/api/src/lib/logger.ts:6-15`. All 5 CLAUDE.md-required fields are redacted (plus phone/email/address), but nested PII (`req.body.borrower.idNumber`, arrays) and query-string PII are not covered.
**Fix:** add wildcard paths (`req.body.*.idNumber`) if nested payloads are ever logged.
